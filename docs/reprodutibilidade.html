Inteligência Artificial como Instrumento de Medição

Capítulo 8 Reprodutibilidade (MLOps)

Um resultado obtido com um LLM só é científico se outra pessoa conseguir refazê-lo. Isso exige versionar não apenas o código, mas também o instrumento e as respostas que ele produziu.

8.2 Um pipeline declarativo com targets

O pacote targets (Landau 2021) descreve a análise como um grafo de dependências: cada etapa declara de quais arquivos depende e quais arquivos produz. Ao rodar targets::tar_make(), só é refeito o que ficou desatualizado. Se você editar o prompt v2, o targets sabe que a validação e a inferência precisam ser refeitas, mas a amostra-ouro e os baselines não.

targets::tar_make()        # roda só o que mudou
targets::tar_outdated()    # o que ficou desatualizado?
targets::tar_visnetwork()  # desenha o grafo de dependências

A coleta e a anotação com o LLM não são refeitas automaticamente: dependem de APIs externas e são caras. Elas entram no pipeline como arquivos versionados, que é o que garante a replicação. Este é o trecho de _targets.R que declara essas entradas:

  tar_target(arq_corpus, "dados/processado/corpus.csv", format = "file"),
  tar_target(arq_referencia, "dados/anotacoes/referencia_completa.csv", format = "file"),
  tar_target(arq_prompts, list.files("prompts", "\\.txt$", full.names = TRUE), format = "file",
             cue = tar_cue(mode = "always")),
  tar_target(arq_cache_llm, list.files("dados/cache_llm", "\\.jsonl$", full.names = TRUE), format = "file",
             cue = tar_cue(mode = "always")),
  tar_target(arq_funcoes, c("R/funcoes_medicao.R", "R/tema_graficos.R"), format = "file"),
  tar_target(arq_scripts, list.files("R", "^0[2-6]_.*\\.R$", full.names = TRUE), format = "file"),

Uma armadilha encontrada na verificação deste material Na primeira versão do pipeline, as entradas arq_prompts e arq_cache_llm eram declaradas apenas com format = "file". Isso detecta edições em arquivos já conhecidos, mas não detecta arquivos novos: o comando list.files() não é reexecutado, porque o código dele não mudou. Na prática, se alguém criasse um prompt v4 ou uma nova execução do LLM, o targets diria que estava tudo atualizado e as tabelas ficariam velhas, em silêncio.

A correção foi acrescentar cue = tar_cue(mode = "always") a essas duas entradas: a lista de arquivos é refeita a cada execução, mas as etapas seguintes só rodam se o conteúdo tiver mudado. O episódio ilustra o ponto deste capítulo: ferramentas de reprodutibilidade também precisam ser testadas.

8.3 R e Python: duas trilhas, os mesmos resultados

O material tem uma trilha completa em Python (notebooks prontos para o Google Colab em python/), que reproduz as mesmas tabelas e figuras. As duas trilhas dão os mesmos resultados, com duas ressalvas: o baseline TF-IDF, já discutido (Capítulo 4), e os números que dependem do gerador aleatório (ICs bootstrap e simulação de cobertura), que diferem em até 0,01 porque R e Python sorteiam de forma diferente mesmo com a mesma semente. Para garantir essa correspondência, até o hash do prompt é calculado da mesma forma nas duas linguagens (leitura byte a byte do arquivo).

8.4 Drift: quando o instrumento muda sozinho

Um questionário impresso não muda entre uma aplicação e outra. Uma API comercial de LLM pode mudar: o provedor atualiza o modelo e o mesmo prompt passa a produzir outra medida. As defesas são:

  • usar um modelo local com versão fixa, como neste material, ou registrar o identificador exato do modelo, a data e as respostas brutas;
  • monitorar: re-anotar periodicamente a amostra-ouro e acompanhar o kappa ao longo do tempo.

Mesmo um modelo local, com versão fixa, não é perfeitamente determinístico. Para medir isso, repetimos em 12/11/2026 as três anotações com temperatura 0, nas mesmas condições: os mesmos pesos (mesmo digest), a mesma versão do Ollama, o mesmo prompt e a mesma semente (python python/anotar_llm.py --todas-t0 --pasta dados/repeticao). Mudaram de rótulo 0, 3 e 2 das 304 ementas com os prompts v1, v2 e v3. A causa são pequenas diferenças numéricas nos cálculos da GPU: quando duas respostas estão quase empatadas, essas diferenças bastam para trocar a mais provável. Não por acaso, uma das ementas que mudaram (doc0233) está entre os casos marcados como ambíguos durante a construção do livro de códigos.

Duas lições. Primeiro, temperatura 0 não garante a mesma resposta: a replicação exata vem do cache das respostas brutas, não de reexecutar o modelo. Segundo, o modelo é só uma parte do instrumento, que inclui também o software que o executa. Atualizar o Ollama pode mudar as respostas, mesmo com os mesmos pesos. Por isso cada registro do cache guarda a versão do Ollama e o digest dos pesos.

8.5 Código gerado por IA

Agentes de programação (Claude Code, Codex e similares) também produzem análises, e cada vez mais. A regra proposta aqui é simples: trate o código gerado por IA como o de um coautor. Ele precisa de revisão, testes e versionamento, e quem o publica responde por ele.

Este livro segue essa regra: foi produzido com o auxílio do Claude Opus 5.5, e o uso está declarado no Apêndice E. Antes da publicação, o material foi verificado de ponta a ponta, com o resultado abaixo.

8.6 Mão na massa: verificar a reprodutibilidade

Como executar

  • Pipeline completo em R, na raiz do projeto: targets::tar_make() refaz amostra-ouro, baselines, validação, inferência e figuras (cerca de 2 minutos), mas só o que estiver desatualizado. targets::tar_outdated() lista o que seria refeito; targets::tar_visnetwork() desenha o grafo (requer o pacote visNetwork).
  • Em Python: rode os notebooks python/01 a 05 em ordem (no Jupyter: Run All; no terminal: jupyter nbconvert --to notebook --execute --inplace python/0*.ipynb). As tabelas vão para resultados/python/tabelas/.
  • Repetir a anotação a temperatura 0 sem misturá-la ao cache: python python/anotar_llm.py --todas-t0 --pasta dados/repeticao (precisa do Ollama).
  • Os blocos abaixo só leem arquivos: nenhum deles refaz o pipeline ou grava resultados.

8.6.2 O cache confere com os prompts?

Uma verificação de integridade simples e poderosa: recalcular o hash de cada prompt e conferir com o prompt_sha gravado em cada resposta do cache. Se alguém editou um prompt depois da anotação, aparece aqui.

source("R/funcoes_medicao.R")
sha_arquivo <- function(arq) {
  txt <- readChar(arq, file.size(arq), useBytes = TRUE); Encoding(txt) <- "UTF-8"
  substr(digest::digest(txt, algo = "sha256", serialize = FALSE), 1, 12)
}
atuais <- tibble(arq = list.files("prompts", "\\.txt$", full.names = TRUE)) |>
  mutate(prompt_id = str_extract(arq, "v\\d"),
         sha_atual = purrr::map_chr(arq, sha_arquivo))
carrega_llm() |>
  left_join(atuais, by = "prompt_id") |>
  count(prompt_id, prompt_sha, sha_atual, confere = prompt_sha == sha_atual,
        digest = modelo_digest, ollama = ollama_versao)

O que está sendo executado. Para cada arquivo de prompt, calculamos o SHA-256 do conteúdo (os 12 primeiros caracteres bastam para identificá-lo) e juntamos ao cache pelo prompt_id. Todas as 1824 respostas conferem com os prompts atuais, vieram dos mesmos pesos (mesmo digest) e da mesma versão do Ollama. Note que a versão Python lê os bytes do arquivo; a versão R lê o arquivo byte a byte (useBytes = TRUE) pelo mesmo motivo: o hash precisa ser idêntico nas duas linguagens.
